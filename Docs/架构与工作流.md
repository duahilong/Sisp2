# 架构与工作流

## 分层

- 入口：`app/gui_web/main.py`（唯一入口，桌面窗口与 `--serve` 浏览器模式共用）。它装配 WebApi、工作流和 FastAPI；命令行入口 `app/cli.py` 已移除，全部能力都在界面里。
- HTTP/UI：`app/gui_web/server.py` 将 REST/SSE 转换为 WebApi 调用；`api.py` 包装响应信封、转发工作流并缓冲事件；`ui/index.html` 是只含布局骨架的薄壳，界面由 `ui/css/app.css` 与 `ui/js/*.js`（ES 模块，`/static` 托管）组成。
- 专项能力：`modules/boot`（ESP 扫描 + `bcdboot` 修复）、`modules/image`（列目录 + GHO 文件头校验，纯文件读取）与 `modules/ghost`（Ghost 命令行拼装）是只被 REST 层调用的独立模块，写盘仍复用服务层的闸门。硬盘分区没有独立模块：布局在 `application/partitions.py`，diskpart 脚本拼装与执行在 `application/real_runner.py`（历史上那套同名「单盘分区工具」已整套移除，`tests/test_partition_tool_removed.py` 钉住 `app/modules/partition/` 必须不存在）。
- 应用：`application/workflow.py` 管理会话、预检结果、扫描快照、计划及确认；`service.py` 提供扫描、配置检查、盘符分配与安全执行门；`partitions.py` 是分区布局（EFI / Windows / 数据分区）的唯一真相；`jobs.py` 管理状态、调度、取消和事件。
- 执行与能力：`real_runner.py` 调用 Windows 系统工具；`preflight.py` 读配置并做启动检查；磁盘扫描、设置、盘符分配等位于 `modules/` 与 `drive_letters.py`。

## 一次工作流

1. `WorkflowController.start()` 运行预检、从设置算出任务载荷（`TaskPayload`）并扫描硬盘，应用系统盘/启动盘/离线/只读/含系统盘符这几条保护规则（型号黑名单功能已整条移除）。
2. `refresh_disks()` 可重新扫描，不改变检查结果。
3. `prepare()` 根据选盘与配置构造分区计划、盘符、身份快照及检查/阻断信息。优先级从弱到强是：设置页默认值 → 向导里这块盘的逐盘覆盖（业务配置那一层已移除；曾经的三层顺序还反过一次，设置会把用户在第 2/3 步填的大小与镜像改回去）。盘符分配会避开磁盘摘要、系统盘符以及 OS 层已占用/遗留的“幽灵盘符”（例如 EFI 隐藏卷留下的 DriveInfo 条目）。**镜像在这一步就要“可应用性”校验**：ISO 直接拒（Ghost 只能还原 GHO）、WIM/ESD/SWM 直接拒（dism 路线已移除）、后缀不是 GHO/GHS 也拒、文件头不是 Ghost 签名（`FE EF`）也拒、找不到 `ghost64.exe` 也拒——都会变成 `plan.blockers` 并让“开始”置灰，避免“清完盘才发现镜像用不了”。

**分区布局是显式模型**：`app/application/partitions.py` 的 `plan_partitions()` 把 `partition_info` 解析成 `[EFI, Windows, Data(, Data2)]`，真实执行器拼 diskpart 脚本、容量预检、dry-run 预览、界面第 4 步摘要都消费同一份结果（以前这三处各写一遍，加一个分区要改三处）。向导第 2 步可以再加一个数据分区（E）：此时 payload 用 `data_partitions` 列表逐项给大小与文件系统（NTFS/exFAT）。
**最后一个数据分区默认让 diskpart 吃掉剩余空间**（`size_mb=None` → `create partition primary` 不带 `size=`）：
比界面自己算「总容量 − C − EFI − 对齐余量」更准，也不会出现「界面上刚好、diskpart 报空间不足」。
计划表里它显示为 `剩余空间（约 X GB）`，但实际大小仍由 diskpart 决定（`estimate_mb` 只用于展示）。盘符按角色分配：`efi` / `windows` / `data` / `data2`，每块盘 3 个或 4 个。

第 2 步的容量条有两条可拖分隔条：**C|D** 改系统分区（变化由 D 吸收，E 不动），**D|E** 只调整两个数据分区的比例（D+E 总量不变）。两者都做了下限钳制（C ≥ 60 GB、D ≥ 20 GB、E ≥ 1 GB）并向下取整，所以拖动**永远不会超过硬盘真实容量**；加 E 时默认与 D 平分剩余容量。E 的文件系统不在界面上单独选择——它与 D 一致，恒为 NTFS（`dataFs()`）。
4. `submit()` 默认创建等待确认的任务；`confirm()` 对无阻断的任务开始调度。放行即授权（界面上已勾选“我明白这些分区会被删除”），确认时会按任务盘号重新补齐隐式白名单——刷新页面会重开会话并撤销隐式授权，不补就会“确认时报白名单为空”。
5. JobManager 调用服务执行任务。真实服务在执行前检查 dry-run 策略、白名单、身份复核及执行器；执行器按分区、镜像、引导（写 + 验）步骤调用系统命令，并在任务结束后释放 EFI 盘符（避免隐藏卷盘符在下次清盘后残留成幽灵盘符）。**释放时按“磁盘号 + 分区号”定位 ESP**（计划时的字母只保证当时空闲，`select volume <字母>` 是按字母选卷的，可能摘掉别人的盘符；按分区定位则与字母无关；ESP 是隐藏卷，`Get-Partition -DriveLetter` 这类按字母的查询看不到它）。**“装完能不能开机”由两道检查合起来判定**（分区验收 `layout` + 引导校验 `boot`）：分区表是 GPT、分区数**等于**计划分区数（三分区布局是 3，加 E 是 4）、盘上没有 Reserved/MSR 分区、盘上没有大块未分配（最后那个分区吃满）；引导校验（`boot` 步骤的后半段）查 EFI 分区里真的有 `EFI\Microsoft\Boot\bootmgfw.efi`（或 `EFI\BOOT\BOOTX64.EFI`）、系统分区里真的有 `Windows\System32\config\SYSTEM`（或 `ntoskrnl.exe`）；缺一项就判失败，并把证据写进步骤 `details`。
6. 运行结果由任务状态和事件返回；取消为协作式，已运行的系统命令不会因此立即中断。

## 多盘并发（分区串行 + 镜像交错）

一次提交多块盘时**不是全串行、也不是全并行**，而是一条流水线：

```
盘 1: [分区+验收]────┐
                      └→ [Ghost 写镜像]→[bcdboot+校验]
盘 2:      [分区+验收]────┐
                            └→ [Ghost 写镜像]→[bcdboot+校验]
盘 3:            [分区+验收]────┐
                                  └→ …
```

- **分区组全局串行**（`PartitionSequencer`，按盘号升序）：diskpart 是全局状态机，
  两块盘同时 `select disk` / `create partition` 会互相踩；同一时刻也只有一块盘在分区，
  所以“盘符池给每块盘分配不同字母”不需要全局锁。
- **系统组各自并行**：一块盘的分区组一结束，它立刻开始自己的 Ghost + bcdboot，
  同时放开下一块盘分区。这就是全部收益来源。
- **失败不连坐**：某块盘分区/验收失败，该盘的系统组记「未执行」，后续盘照常分区与写镜像。
- **取消是分档的**：排队等分区的盘直接记「任务已取消（排队中）」并且一个命令都不跑；
  正在分区的盘在步骤边界停；已经在写镜像的盘按 Ghost 的协作式取消处理。

实测收益（分区+验收 40 s / 镜像 300 s / 引导 10 s）：3 块盘 1050 s → **430 s**，
6 块盘 2100 s → **550 s**（`Docs/多盘并发改造实施文档.md` 与 `Docs/多盘并发时间线.drawio`）。

**为什么 Ghost 之间要留 2.5 s**：Ghost 11.x 在同一瞬间启动两个实例时，后启动的一方会在
“卷枚举”阶段以 `Error Number: (8027) / A GeneralException occurred / The device is not ready`
退出（还没写数据）。错开 2 s 即正常（VM 上 3 盘 × 2 s 错开：3/3 成功，总时长 41 s，
顺序执行需 112 s）。流水线里这个间隔天然等于“下一块盘的分区时长”，`GhostStartGate`
只是保险：`min_gap=2.5s`，可注入时钟便于测试。

**并发不降低任何闸门**：白名单、身份复核、保护规则都在每个任务执行前各自跑一遍；
`diskpart` 调用另有一把模块级锁（分区、释放盘符、boot 修复都会用到）；每个任务拥有
独立的 Ghost 工作目录（`sisp-ghost-<盘号>-*`，临时目录），失败时的 `GHOSTERR.TXT` 会
复制成 `logDir/ghosterr-disk<盘号>-<时间>.txt` 再删目录——共用目录会让两块盘的失败原因
互相覆盖。执行日志文件名也加了进程号 + 随机后缀。

并发度不是设置项：`WorkflowController(max_parallel=0)` 表示“按本批任务数放开”，
`worker_interval=0`（不再人为错开任务启动）。单盘任务时序与历史实现完全一致。

## 分区时的 MSR 处理

`convert gpt` 会**自动**在盘首建一个约 16 MB 的 MSR（Microsoft Reserved）分区——这不是我们脚本里的命令，是 Windows 的行为（Windows 10 19045 / diskpart 10.0.19041 实测：`p1 Reserved 15.98 MB`，GPT 类型 `e3c9e316-0b5c-4db8-817d-f92df00215ae`）。产品要求的最终布局是 **EFI + C + D(+E)**，没有 MSR，所以执行器把分区拆成**三段 diskpart + 两次复核**：

| 阶段 | 做什么 | 失败时 |
| --- | --- | --- |
| ① 清盘 | `select disk N` → `clean` → `convert gpt` → `exit`（MSR 就是这一步自动出现的，`tracker["diskpart_ran"]` 在这里置位） | 立即失败，不碰后面的步骤 |
| ② 删 MSR | PowerShell 按 GPT 类型查分区号 → `select disk N` / `select partition k` / `delete partition override` / `exit`，**单独一段脚本** | 退出码非 0 → 立即失败 |
| ②' 复查 | 再查一次：还查得到 MSR → 中止，**绝不继续建分区** | 报“MSR 分区删除失败：删除后仍然存在（分区 #k）” |
| ③ 建分区 | `select disk N` + `diskpart_lines(parts)`：EFI → C → D(+E)，最后一项不带 `size=` | 退出码非 0 → 立即失败 |
| ③' 验收 | 对照计划逐项验证（见下一节），任何一项不符 → 分区阶段失败 | 在跑 Ghost 还原（最长 2 小时）**之前**就报错 |

为什么不在清盘脚本里直接写 `select partition 1` + `delete partition override`：万一某台机器没自动建 MSR，`select partition 1` 会报错，**整条 diskpart 脚本会中止**，装机直接失败。所以只对“查到的 MSR”动手：

- 查到 → 删掉并复查（删完后盘首空闲与后面合并，实测 EFI 依然落在 `offset=1 MB`，不会留 16 MB 空洞）；
- 查不到 → 不删任何东西，直接建分区；
- **查询本身失败（PowerShell 报错/超时）→ 中止任务并报错**，绝不猜一个分区号去删（猜错就是删掉真分区）；
- 查询带重试（3 次 × 300 ms）：`convert gpt` 刚结束时慢盘/RAID/USB 桥接上的分区枚举可能还没跟上，一次查不到就跳过删除会把 MSR 留在盘上。

为什么不靠 diskpart 的退出码判定成功：不同 build 对“某条命令失败”的退出码行为并不一致（19041 实测返回非 0，但别的版本有返回 0 的记录），所以第二段、第三段之后都各自查一次真实分区表。

代价：盘上没有 MSR 后，动态磁盘转换、部分内核内存转储、某些 BitLocker 配置会受限——这是产品明确接受的取舍。演练预览（`build_diskpart_preview()`）把三段都展示出来，MSR 那两行以 `REM` 形式出现（预览时不知道真实分区号）；第 4 步的分区行只列 EFI / Windows / 数据分区，MSR 不再单列（它是 `convert gpt` 的临时产物，执行完会删，日志里有完整脚本）。

## 分区阶段与写入镜像阶段是分开的（代码也已经拆开）

**流程上分开**是一回事，**代码单元上分开**是另一回事。现在两者都做了：

```
app/application/
├─ steps.py                 步骤 / 阶段契约（纯数据）：7 步 = 分区 4 + 系统 2 + 收尾 1
├─ partitions.py            纯函数：布局、三段脚本生成、分区验收判据
├─ command_log.py           执行日志（三段共用）
├─ shell.py                 ProcessShell / DiskpartShell：唯一的 spawn 出口 + 护栏
├─ phases/
│   ├─ partition.py         PartitionPhase（清盘/删 MSR/建分区/验收）+ EfiLetterReleaser
│   ├─ ghost.py             GhostImagePhase（ghost64 -clone）
│   ├─ copy.py              CopyAssetsPhase（robocopy 拷附加文件到第一数据分区）
│   └─ system.py            SystemPhase = 镜像 + UefiBootPhase（写引导并校验）
├─ uefi/
│   ├─ target.py            BootTarget：从 PhaseContext 提盘符 / 引导源
│   ├─ writer.py            BcdbootWriter：拼 bcdboot 命令行并执行
│   ├─ probe.py             BootProbe + boot_verdict：查引导文件 + 系统文件
│   └─ phase.py             UefiBootPhase：写 → 验的阶段门面
├─ pipeline.py              JobPipeline：组顺序、失败跳过、取消检查点、收尾
└─ real_runner.py           只剩"组装 + 翻译成 WorkerResult"
```

阶段之间只通过 `PhaseContext` / `PhaseOutcome` 交换信息：分区阶段回答
"成没成功、盘动过没有、ESP 是第几号分区"，系统组读自己的入参。
**分区阶段不 import Ghost / bcdboot，也不读 `image_info`**；"要不要继续"只有
`pipeline.py` 知道（`tests/test_phase_pipeline.py` 用源码扫描与调用计数钉住这两条）。

| 组 | 步骤 | 失败后可执行性 |
| --- | --- | --- |
| `partition` | `efi` / `windows` / `data` / **`layout`（分区验收）** | 失败 → 系统组全部记为 `skipped`，盘上没有写入任何镜像数据 |
| `system` | `image`（Ghost 还原 GHO）/ `boot`（bcdboot 写引导 + 查引导/系统文件） | 失败即为任务失败；EFI 临时盘符照常释放 |
| `extras` | `copy`（robocopy 把整个文件夹拷到第一数据分区根下，目标为 `<盘符>:\<文件夹名>`；设置留空则 skipped） | 失败即任务失败（该盘流程没走完）；重装时会跳过 |

`layout` 是独立的一步：以前分区验收被塞在 `data` 步骤的 `details.verification` 里，
界面上看不出来；现在进度条上有它、失败原因挂在它自己的 `details` 里（`problems` /
`warnings` / `actual` / `efi_partition`）。

### 镜像写入（Ghost）

装机只走 Ghost 一条路（dism/WIM 路线已移除），命令由 `modules/ghost/service.py` 纯拼装、
`phases/ghost.py` 执行：

```
ghost64.exe -clone,mode=pload,src=<GHO 路径>:1,dst=<Ghost 磁盘号>:<分区号>
            -sure -batch -ntexact
```

三个约定：

- **`dst` 是 Ghost 自己的 1 基编号**：`disk_number + 1` 与"Windows 在计划里的位置（EFI=1、
  Windows=2）"，换算函数是 `partitions.ghost_target()`；分区验收保证计划位置 = 实际分区号；
- **`src` 的 `:1` 是镜像内部的第一个分区块**（不是目标分区号），由 `modules/ghost/service.py:IMAGE_BLOCK_INDEX` 固定，不开放设置；
- **绝不加 `-rb`**：还原之后还要跑 `bcdboot`。`-batch` 让 Ghost 跑完自动退出（否则进程停在
  结尾等按键，父进程只能等到超时）；`-ntexact` 是 NTFS 按原样还原（与原型一致）。

失败诊断：Ghost 把原因写进**当前工作目录**的 `ghosterr.txt`，所以执行时 `cwd` 指向日志目录，
退出码非 0 时把 `ghosterr.txt` 尾部与 stdout 尾部一起挂进 `image` 步骤的 `details`。

### 两个"验收"不要混

| 名称 | 步骤键 | 什么时候跑 | 看什么 |
| --- | --- | --- | --- |
| 分区验收 | `layout` | Ghost 还原**之前** | GPT、分区数、顺序与类型、大小、盘符、卷标、文件系统、容量闭合、盘已吃满 |
| 装机结果校验 | `boot`（第二步） | 镜像与引导都写完之后 | EFI 里有没有 `bootmgfw.efi`、系统分区里有没有 `Windows\System32\config\SYSTEM` |

### 收尾：拷贝附加文件（`copy`）

设置页「安装默认值 → 拷贝文件目录」留空时这步记 `skipped`、任务照常成功；填了就属于
流程的一部分，**失败即整盘失败**（`GROUP_STOP_ON_FAILURE["extras"] = True`）。

```
robocopy <源目录> <第一数据分区盘符>:\ /E /COPY:DAT /DCOPY:DAT /XJ /R:1 /W:1 /NFL /NDL /NJH /NJS
```

- **目标是计划里第一个 `role="data"` 的分区**（不是按盘符字母猜；加额外分区 E 时仍是 D），
  `partitions.plan_partitions()` 的顺序就是真相；
- `/COPY:DAT` + `/DCOPY:DAT` 保属性（隐藏/系统/只读）与时间戳，`/E` 建空目录；
- **绝不含 `/MIR` `/PURGE` `/MOV`**：目标分区原有文件不会被删；`app/safety_guard.py` 另有一道拦截；
- 退出码 0–7 算成功；拷完用 `compare_trees()` 逐文件比「相对路径 + 大小 + 修改时间(±2 s) + 隐藏/系统/只读属性」，
  差异直接让该步失败并列前 5 条；
- 拷前预检：源目录不可用 / 没有数据分区 / 数据分区没盘符 / 源与目标重叠（会递归）/ 空间不足，
  都先失败，不发命令；
- 多盘时每块盘各拷一次（同一源目录 → 各自的 D:\)，与 Ghost 一样随自己的系统组并行。

### 进度与前端编排

`JobManager` 的 `job.progress` 在原有字段上增加 `groups`（按组算百分比），
`POST /api/prepare` 的 `plan.phases` 是声明式编排：

```json
[{"key": "partition", "title": "硬盘分区", "steps": ["efi", "windows", "data", "layout"], "stop_on_failure": true},
 {"key": "system",    "title": "写入系统", "steps": ["image", "boot"], "stop_on_failure": true},
 {"key": "extras",    "title": "收尾",     "steps": ["copy"], "stop_on_failure": true}]
```

前端不再硬编码步骤表：`derive.js` 的 `phaseGroups / progressByPhase /
skippedByFailure / layoutVerdict` 都是纯函数（`tools/ui_check.py` 在 node 里真跑断言），
进度页因此是"硬盘分区 / 写入系统 / 收尾"三段，分区失败时后两段显示
「未执行（前一段没有通过验收）」，并展开分区验收明细。

进度页按**每盘一张卡片、固定 3 列**排布（`grid-template-columns: repeat(3, minmax(0,1fr))`，
窄屏降 2 列 / 1 列），卡片里只有一行头部（盘号 + 状态徽标 + 百分比）、一行当前动作、
4px 进度条和 **3 行阶段**（①硬盘分区 ②写入系统 ③收尾）；每一步的细节、分区验收明细与
任务日志都收进 `<details>`，默认折叠。重绘每 1.5 s 一次，`captureOpenDetails()` 会把用户
展开过的 `details[data-open-key]` 记下来再恢复，否则刚点开的阶段会被合上。
底部 `.progfoot` 常驻（sticky）：取消按钮是实心红 `.tbtn.danger`，完成后换成「完成 / 重试 / 查看任务日志」。

### 预览与真跑同源

`SispService.build_diskpart_preview()` 与新增的 `POST /api/partition/preview`
都调用 `partitions.preview_segments()`——和真实执行器是同一套行生成器
（`wipe_lines` / `msr_delete_lines` / `create_partition_lines`），
所以"预览和真跑不一样"在机制上不再可能（`test_phase_pipeline.py` 有逐行断言）。

### 测试怎么注入

测试不再写 `runner._run_diskpart = fake`（实现搬家后会静默失效，2026-11-06 事故的形态），
改用构造期注入：`WindowsDiskRunner(shell=FakeDiskpartShell(...), process=FakeProcess(...))`，
或直接单独测 `PartitionPhase(FakeShell())` / `SystemPhase(FakeProcess())`。
替身定义在 `tests/fakes.py`，夹具见 `tests/conftest.py`。

## 盘符池与批量上限

`app/drive_letters.py` 的池子是 **E–Z（22 个）+ A/B 兜底（2 个）= 24 个**：

- E–Z 优先；A/B 只在字母紧张时才用。现代 Windows（无软驱）允许把 A:/B: 分给固定磁盘，
  `bcdboot /s A:` 都实测可用；但少数老程序看到 A:/B: 会当成软驱，
  所以顺序上放最后，正常装机不会出现 A:/B:。
- C/D 永远不进池（系统盘/光驱习惯位）。

盘符是 **`prepare` 阶段一次性静态分配**的（`build_drive_letter_allocations(选中的盘, 已占用字母)`），
每块盘按布局要 3 个（EFI + C + D）或 4 个（再加 E），所以**一次提交的上限**是：

| 布局 | 每盘字母 | 一次提交上限 | 用满时的分配 |
| --- | --- | --- | --- |
| EFI + C + D | 3 | **8 块**（24） | 第 8 块 `Z / A / B` |
| EFI + C + D + E | 4 | **6 块**（24） | 第 6 块 `Y / Z / A / B` |

再多就报 `可用盘符不足，无法为硬盘 N 分配 4 个盘符（剩余 k 个可用）`，`prepare` 直接失败。

注意两点：

1. **EFI 释放开关不影响这个上限**——开关只决定任务跑完之后字母回不回池，分配时总要占。
2. **批次之间会累积占用**：任务结束只释放 EFI（默认），Windows/Data 的盘符一直挂在当前系统里，
   所以下一批 `prepare` 的可用字母会变少（`forbidden` 来自当前已用卷）。
   实测：第一批 6 块 × 4 分区跑完，池内被占 18 个字母（Windows/Data/Data2 各 6 个），
   只剩 6 个，第二批只能再勉强塞 1 块（4 个字母），第 2 块就报不足。

真正突破 24 个字母的办法是“运行时动态分配”（串行执行时同一时刻只需要 3–4 个字母）或改用
挂载点（`assign mount=`），目前**没有做**，所以批量上限就是 8 块（三分区）/ 6 块（四分区）。

## EFI 盘符的生命周期

ESP（EFI 系统分区）在 Windows 里是隐藏卷：`Get-Partition.DriveLetter` 对它永远为空，
即使临时挂了字母也一样，只有 `Win32_LogicalDiskToPartition` 能关联出那个字母。所以
执行器按「磁盘号 + 分区号」定位它，不按字母找归属。

盘符的时间线：

| 时机 | 动作 |
| --- | --- |
| 阶段 1/3 建分区 | EFI 分区 `assign letter=<efi>`（计划里的字母，来自 `drive_letters.py` 的盘符池） |
| 阶段 2/3 镜像 | 用不着 EFI 盘符（Ghost 只写 C 分区，`dst=<磁盘>:<分区>`） |
| 阶段 2/3 引导 | `bcdboot <C>:\Windows /s <EFI>: /f UEFI`——**必须还挂着字母** |
| 阶段 3/3 校验 | 通过同一个字母检查 `\EFI\Microsoft\Boot\bootmgfw.efi`、`BOOTX64.EFI` |
| 任务收尾（`finally`） | `_release_efi_letter_if_enabled()`：默认 `remove letter`，摘掉临时盘符 |

释放动作是唯一的、独立的入口（`_release_efi_letter_if_enabled`），在 `run()` 的
`finally` 里只调一次，受设置 `releaseEfiLetter` 控制：

- **开（默认）**：按「磁盘 + 分区号」发 `select disk N` / `select partition k` /
  `remove letter=X`，避免隐藏卷的临时盘符残留成幽灵盘符（残留会让下次 `clean` 后
  的 `assign letter` 失败）；
- **关**：一条 diskpart 都不执行，连 ESP 分区号都不查，只写日志
  「已关闭 EFI 盘符释放（设置 releaseEfiLetter=false），保留 E:」。

关掉之后的代价：盘符一直占着（用户可用盘符少一个），而且下次对这个盘 `clean` 之后，
旧盘符会变成指向不存在卷的幽灵盘符。适合“装完想手动进 ESP 看一眼引导文件”的场景。

## 分区阶段的验收（对照计划逐项验证）

建完分区后立刻查一次真实分区表 + 卷信息，交给纯函数 `_partition_verdict()` 对照计划检查。
**这一步只看“分区做对没有”**，不要求镜像/引导已写入，所以能在 Ghost 还原之前拦住问题。

| 检查项 | 判据 | 实测依据 |
| --- | --- | --- |
| 分区表 | 必须是 GPT | |
| 分区数 | == 计划分区数（3 或 4） | `convert gpt` 的 MSR 必须已删 |
| 无保留分区 | 盘上不能有 Reserved/MSR | |
| 顺序与类型 | 按 offset 排序后第 i 个分区：EFI → ESP GUID（`c12a7328-…`），C/D/E → Basic Data（`ebd0a0a2-…`） | 建分区总从盘首第一个空闲区分配 |
| 大小 | 显式项（EFI、C、有 E 时的 D）\|实际 − 计划\| ≤ 1 MB；最后那个 auto 分区用“剩余”核对 | `Get-Partition.Size` 是 1 MB 对齐的 |
| 盘符 | 计划盘符必须真的挂在这个分区上：C/D/E 用 `Get-Partition.DriveLetter` 硬校验；ESP 的临时字母在隐藏卷上查不到，用 WMI `Win32_LogicalDiskToPartition` 关联查，查不到只告警 | 实测 ESP 的 `Get-Partition` 盘符为空、WMI 能给出 |
| 卷标 | `EFI` / `Windows` / `Data` / `Data2` 与计划一致（忽略大小写） | `Get-Partition \| Get-Volume` 对 ESP 也能读到卷标 |
| 文件系统 | `FAT32` / `NTFS` / `exFAT` 与计划一致 | 同上 |
| 容量闭合 | `sum(实际分区) + 2 MB == 盘容量`（±2 MB） | GPT 首尾各 1 MB |
| 盘已吃满 | `LargestFreeExtent ≤ 2 MB` | 最后一个分区不带 `size=` |

失败信息带定位与数值，例如：

```
第 2 个分区（Windows）大小不符：计划 122880 MB，实际 102400 MB
第 2 个分区（Windows）盘符不符：计划 K:，实际 I:
第 3 个分区（Data）卷标不符：计划 Data，实际 Data9
第 1 个分区（EFI）没有挂上计划盘符 H     ← 只告警（ESP 临时字母收尾就释放）
盘上有 50 GB 未分配（最后分区应当吃满）
```

验收结论同时写进 `data` 步骤的 `details.verification`（`message` / `problems` /
`warnings` / `actual`），界面和日志都能直接看到“计划 vs 实际”。

## 最后一个数据分区永远吃满

**界面永远把最后一个数据分区发成 `"auto"`**（`selectionPayload()`），diskpart 收到的是不带 `size=` 的 `create partition primary`，尺寸由它自己算。所以：

- 界面上 D / E 的数字只是**预估**（`fitLayout()` 算出来的，用于显示和拖动），最后那个分区的输入框是只读的（`.szrow input[readonly]`）；
- 没有 E 时，D 就是那个 auto 分区 —— 也就是说“把 D 调小、留一块未分配”这个能力已经取消，盘总是被填满；
- 有 E 时，D 是显式分区（可编辑），E 是 auto；
- 容量校验（`partitions.check_layout()`）只算**显式项**：EFI + C +（有 E 时的 D）。显式项留 3 MB 余量（`LAYOUT_SLACK_MB`：GPT 盘首 1 MB + 盘尾 1 MB + 1 MB 冗余），实测 40 GB 盘显式合计 = 容量 − 2 MB 时 diskpart 成功、= 容量 − 1 MB 时最后一个 `create` 失败（`exit=-2147024809`）；
- 界面上不再有“未分配”这个概念：第 2 步进度条没有灰色段、第 4 步的分区行没有“未分配”，最后那个分区显示成“剩余空间（约 X GB）”；
- **改 C（或改显式的 D）时，最后那个分区的预估值要立刻重算**（`state.syncAutoPartition()`，在输入框 `input`、失焦、以及每次渲染第 2 步前都会跑）。它的输入框是只读的、不会自己触发 `input` 事件，所以 `updateSizeVisual()` 还要把新值写回输入框——否则用户看到的是“C 改成 116，D 还停在 276.6，两个数加起来不等于整块盘”。

## 分区大小下限（后端也拦）

界面的第 2 步有表单校验（`MIN_SYS_GB = 60`、`MIN_DATA_GB = 20`、`MIN_EXTRA_GB = 1`），
但那只是**表单**：直连 `POST /api/prepare` 可以传 `c_size_gb = 1`，旧实现会一路排到
Ghost 还原才失败——而那时候盘已经清空了。现在后端也有同一套下限（`partitions.MIN_C_GB`
等，`tests/test_partition_layout.py` 会把两边的常量钉在一起），生效在两处：

1. `workflow._check_partition_fit()`：计划阶段就报“硬盘 N 分区过小：…”，`/api/prepare`
   直接失败，**不会生成 executable=true 的计划**（演练同样拦，避免“演练绿、真跑红”）；
2. `WindowsDiskRunner._run_steps()`：`plan_partitions` 之后、`_wipe_script` 之前再拦一次，
   保证绕过 `prepare` 直接塞 JobSpec 的调用方也不能在盘上建出 1 GB 的系统分区。

最后那个 auto 分区没有显式大小，按“容量 − 显式项 − `LAYOUT_SLACK_MB`”估算，够不够
它自己的下限同样会拦（与界面 `checkLayout()` 的判断一致）。

单测需要低于下限的布局时，直接在构造好的 payload 里写 `partition_info.allow_small_partitions: true`。
注意这个键**没有外部入口**了：界面从不发它，`/api/prepare` 的逐盘覆盖也不认它（业务 JSON
配置文件那一层已移除），所以真机/VM 实测必须给 ≥ 100 GB 的盘；8 GB 小盘只能用单元测试
（直接把 payload 交给 `plan_partitions` / `prepare`）验证。

## 演练与真实模式的判定

`SispService` 构造默认 `dry_run=True`，入口会覆盖其策略。`main.py` 的有效 dry-run 只来自命令行 `--dry-run`（设置里的默认演练开关已移除）；`WorkflowController` 会把构造时的 dry-run 锁定为硬上限，后续 `start()` / `prepare()` 只能降级为演练，不能升级为真实执行。真实模式下，`prepare()` / `authorize_disks()` 会把本次勾选并确认过的盘加入服务白名单（没有显式白名单文件）。见[安全说明](安全边界.md)。

## 前端结构

三个视图（主页面、系统安装、设置）+ 一个外壳，不引入框架、也没有构建步骤：

- `js/state.js` 是唯一可变状态：磁盘快照、选中项、设置草稿、任务、执行计划、向导进度；写状态后调 `notify()`。
- `js/view-*.js` 只读状态并返回/写入 DOM；`js/shell.js` 包掉菜单、工具栏、日志坞、状态栏、toast、弹窗、主题与密度；`js/derive.js` 是纯函数层（容量格式化、分区地图切片、大小校验），能在 `node` 里直接跑。
- 弹窗四个（修复引导、磁盘检查、关于、快捷键），都在 `js/dialogs.js`；单盘分区工具（`/api/partition/*`）已于 2026-11 移除，分区只走装机向导。
- 主页面只读：分区地图与明细表都来自 `GET /api/disks` 的快照，不允许在这里发起写盘。
- 写盘只有一条链路：`POST /api/prepare` → `submit` → `confirm`。界面不自己拼 diskpart/Ghost 命令，也不自己算盘符：向导第 4 步显示的盘符来自 `plan.drive_letters`，第 2 步填的大小（含可选的额外数据分区 E）只是 `prepare` 的入参，后端 `_check_partition_fit` 还会再验一次。
- 向导第 4 步只留三块信息：每盘一张 `.pcard`（磁盘/型号/容量 + 逐行分区含盘符 + 镜像 + 模式，`partition_plan` 为空时才按设置估算）、一行 `.warnline`（危险提示 + `<details>` 折叠“查看将丢失的分区”）、唯一的勾选栏 `.ackbar`；「开始安装」只出现在底部工具栏的 `#wzNext`（第 4 步文案切为「开始安装」，点下去直接提交，不再弹二次确认框），diskpart 脚本预览折叠在卡片里首次展开才请求。后端是逐盘给 `blockers` / `warnings` 的，界面用 `derive.js` 的 `mergePlanNotes(plans, key)` 按提示正文合并：同一句话只出现一行，行尾用 `.ntag` 标出涉及哪些盘（`磁盘 1 / 2`），避免多盘时同一句提醒重复 N 遍。
- 进度不是前端“估”的：执行器通过 `on_step` 回调把每个步骤的状态交给 `JobManager`，变成 `job.step` 事件和 `Job.progress`（详见 [Web API 文档](Web接口与部署.md)）。
